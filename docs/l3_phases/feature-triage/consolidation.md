# B. 統合・廃止（引き算）

削除・統合はユーザーへの影響が大きく元に戻しにくいので、**どの項目もオーナー確認（[README](README.md)「オーナーに確認したいこと」）を通してから**着手する。実装するときは、旧 URL を無視するか既定に寄せ、localStorage キーは変えず、revert 1 回で戻せる単位にする。

---

## B1. 見たい/見たの絞り込みを URL に載せ、戻っても消えないようにする ★推奨 2

> **オーナー回答（2026-10-17）**: ♥と「見たい」は別の意味で使っている／「見た作品だけ」の絞り込みも使う。→ 統合も置き換えもせず、**いまの意味のまま、持ち方だけ直す**。下の「現状」のうち、L1 との向きの違いと ♥・見たいの重なりの 2 点は、実装ではなく **L1 REQ-0015 の文言をいまの使い方に合わせて直す**。

**対象ファイル**: `web/src/main.ts:68-73, 486-495, 631-733`、`web/src/features/router.ts`（`ListState`・`LIST_PARAMS`）、`web/src/features/list/filter.ts`（`FilterOpts`）、`web/src/features/list/list.ts`（`MARK_META`・サイドバー）、`web/src/features/shared/user-state.ts`、`web/src/features/detail/detail.ts`。

**現状（根拠）**

- 軸が 2 つある: ♥お気に入り（2 値）と、視聴状態（1 つのボタンを押すたびに 未視聴→見たい→見た→未視聴 と巡回）。
- **持ち方がばらばら**: ♥のフィルタは URL（`fav=1`）、見たい・見たのフィルタはメモリ上の `let`。一覧→詳細は通常のリンク遷移（フルリロード）なので、**詳細から戻ると見たい/見たのフィルタだけ消える**。スクロール位置は戻るのに絞り込みは戻らず、挙動が食い違う。
- **L1 とフィルタの向きが逆**: REQ-0015 は「♥お気に入りだけ／**✓未視聴だけ**」を求めている。実装の「見た」フィルタは**見た作品だけを残す**。いちばん多そうな用途の「見たものを除いて探す」ができない。
- **♥と見たいの意味が重なる**: REQ-0015 は ♥の目的を「気になる作品を後で」と書いているが、それは「見たい」そのもの。
- **巡回ボタンは押すたびに結果が変わる**: 見た → 1 回押す → 未視聴、で記録が消え、取り消す手段も無い。「同じ操作で同じ結果」に反する。

**提案**

1. **見たい・見たの絞り込みを URL に載せる**（例 `mark=fav,want,watched`。旧 `fav=1` も引き続き受け付ける）。`improvement/phase3.md` §3 の URL 化と同じ PR にまとめる。意味（含める＝その状態の作品だけ残す）は変えない。
2. **L1 REQ-0015 を実際の使い方に合わせて直す**: ♥＝お気に入り、見たい＝これから見る、の別の軸であることと、絞り込みは「見たい」「見た」それぞれの作品を出すものであることを書く。
3. （任意・要望があれば）「見たを隠す」を**追加**する。置き換えはしない。
4. （任意）詳細ページの視聴状態を 3 つのボタン（未視聴／見たい／見た）にする。カードは巡回ボタンのまま。

**L0 整合**: 予測どおり（リロードしても戻っても同じ結果・ボタンの結果が押す前に分かる）。

**価値 / コスト / リスク**: 価値＝高（手元の状態管理は毎回使う）／コスト＝小〜中（web だけ）／リスク＝低（保存データ・localStorage キーには触れない）。

**受け入れ条件・検証**: 一覧で「見たい」または「見た」の絞り込みを ON にして詳細に入り、戻っても ON のまま。リロードしても ON のまま。URL を共有すると同じ結果になる（マーク自体は端末ごと）。旧 URL の `fav=1` は引き続き効く。

## B2. 設定の表示トグル 2 つを 1 つにまとめる

**対象ファイル**: `web/src/features/shared/settings-modal.ts`、`web/src/main.ts:72-76, 413-425, 643-646`、`web/src/features/list/filter.ts`（`includeEmpty`・`showUnavailable`）、`web/src/features/list/list.ts`（適用中チップ）。

**現状（根拠）**

- 「取得できていないシリーズも表示」（話数 0 の空シェル）: **本番で 4 作品**にしか効かない。持ち方はメモリなので、リロードで消える。ON にすると一覧に適用中チップが出る。
- 「取得不可の作品を表示」（`isAvailable=false`）: **本番で 103 作品**。localStorage に保存され、リロード後も残る。こちらはチップが出ない。
- ユーザーから見るとどちらも「取れていない作品を出すか」で同じ意味なのに、保存されるかどうかも、チップが出るかどうかも違う。

**提案**: 1 つの保存されるトグル「配信終了・取得できない作品も表示」（既定 OFF・空シェルと取得不可の両方を対象）にまとめる。ON のときは一覧に適用中チップを出し、その場で解除できるようにする（今の空シェルと同じ作法）。

- 代わりの案（オーナー確認 Q7）: 空シェル側だけ削除（4 作品で、中身が無いので出す価値は小さい）。L1 の非機能要求「配信停止作品はそのまま扱い、欠損を正直に出す」を重く見るなら、取得不可は既定で表示し、バッジで区別する案もある。

**L0 整合**: 選択肢を絞る（同じ意味のスイッチを 1 つにする）。予測どおり（保存のされ方が揃う）。

**価値 / コスト / リスク**: 価値＝小〜中／コスト＝小／リスク＝低（既存の `nico-danime-show-unavailable` キーを引き継げば、既に ON にしていた人の設定もそのまま）。

## B3. トップのランダムタグを 1 本にし、勝手に動かさない

**対象ファイル**: `web/src/features/top/top.ts`（クイックアクセスのマーキー・`populateTags`）、`web/src/components/marquee.ts`。

**現状（根拠）**

- トップの 1 画面に、ランダムなタグの帯が **2 本**ある。クイックアクセス下のマーキー（16 個・自動で流れる）と、「タグから探す」のランダム行（16 個・自動スクロール＋引き直し）。
- 母集団はほぼ全タグ（A4）なので、**チップの約 8 割は 1 作品しか出ない**。表示されるたびに中身が変わり、しかも 2 本とも勝手に動く（`prefers-reduced-motion` のときだけ止まる）。
- 同じセクションの下には、全タグを出現数順に並べた「タグ」の一覧もある。

**提案**: クイックアクセス下のマーキーを削除する。ランダム行は引き直しボタンを残し、**自動スクロールをやめて手で動かすだけ**にする。母集団は A4 の 3 で絞る。どちらを残すかはオーナー確認 Q6。

**L0 整合**: 時間を奪わない（勝手に動くもので注意を引かない）。選択肢を絞る（同じ働きのものを 2 回出さない）。予測どおり（ランダムは 1 か所・自分で引き直す）。

**価値 / コスト / リスク**: 価値＝中／コスト＝小／リスク＝低（`initMarquee` を使っているのはクイックアクセスのマーキーだけ、`initAutoScroll` はランダム行だけ＝両方とも `top.ts` の中で閉じているので、使わなくなった関数はまとめて削除できる）。

## B4. 並び替え 8 種を減らす（オーナー判断・優先度低）

**対象ファイル**: `web/src/features/router.ts`（`SortKey`・`VALID_SORTS`）、`web/src/features/list/filter.ts`、`web/src/features/list/list.ts`（2 列のグリッド）、`web/src/main.ts`（`cardMetric`）。

**現状（根拠）**: 五十音・Hot・累計再生数・平均再生数・最近更新・新規シリーズ・累計コメント数・平均コメント数 の 8 種。本番データで順位の相関（Spearman）を見ると、再生数とコメント数で 0.91、平均どうしで 0.90。ただし上位 50 件の重なりは 27/50、22/50 で、上の方では違う作品が並ぶ（コメントが多い作品＝実況向けの作品が浮く）。

**提案（オーナー確認 Q4）**: 使っていなければ「累計コメント数」「平均コメント数」を外して 6 種にする（2 列×3 行）。コメント数は詳細のメタに残す。旧 URL の `sort=comments` は既存の挙動どおり既定（hot）に戻る。外さない場合も、2 列の対の並び（再生｜平均再生、コメント｜平均コメント）はそのまま意味が通るので、無理に減らす必要は無い。

**価値 / コスト / リスク**: 価値＝小（認知負荷の軽減）／コスト＝小／リスク＝低。

## B6. 使っていないデータを読まない・作らない

**対象ファイル**: `web/src/main.ts:140-161`、`web/src/data/loader.ts`（`loadNew`・`loadKana`）、`scripts/store/project.mjs`（`exportKana`）、`.github/workflows/fetch-daily.yml:175-176`、`scripts/ops-health.mjs`。

**現状（根拠）**

- `new.json`（話単位の新着）: ページを読み込むたびに取得しているが、**どこにも表示していない**（`cache.newData` を参照する箇所が無い）。トップの話単位の列は §73/§74 で廃止されている。一方、`ops-health` の U1（新着の反映遅れ）が使っている。
- `kana.json`: ETL で作り、deploy で存在を assert し、ops-health でも件数を見ているが、**クライアントは一度も読まない**（`loadKana` を呼ぶ箇所が無い）。
- L1 REQ-0010 には「最新の動画（話単位・new.json）: トップに掲載」と書いてあり、実装と食い違っている。

**提案**

1. **クライアントで `new.json` を読むのをやめる**（`ensureData` から外す）。生成は ops-health のために続ける。挙動は変わらず、リクエストが 1 本減るだけなので、すぐやってよい。
2. **話単位の新着枠を戻すかどうか**（オーナー確認 Q8）: 戻さないなら L1 REQ-0010 と screens.md を「新規シリーズ／最近更新の 2 列（シリーズ単位）」に書き直す。**推奨は戻さない**（最近更新の列で毎時の新着も反映されるため）。
3. **`kana.json` の生成をやめる**（任意・優先度低）: ETL・deploy の assert・ops-health・AGENTS.md の「公開 6 本」をまとめて直す必要があるので、運用側の都合がよいときに 1 PR で行う。

**参考（対象外・メモのみ）**: works.json の `franchiseKey`・`mylistTotal`・`mylistFirst` もクライアントでは使っていない。転送量の改善は今回のスコープ外なので、性能トラックで扱う。

**価値 / コスト / リスク**: 価値＝小（混乱の元を減らす）／コスト＝小／リスク＝低。
