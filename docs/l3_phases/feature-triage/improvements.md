## A1. Hot（勢い）を「前日比の再生増」主体にして、数値で見せる ★推奨 1

**対象ファイル**: `scripts/etl/metrics.mjs`、`scripts/store/project.mjs`（`exportWorks`／`exportRanking`）、`web/src/main.ts`（`cardMetric`）、`web/src/features/list/list.ts`・`top/top.ts`（ⓘ 文言）、`web/src/data/types.ts`。2 段階目は state に 1 ファイル追加。

**現状（根拠）**

- 式は `hotScore = 0.5·deltaN + 0.3·riseN + 0.2·baseN`。各成分は log1p をかけてから全シリーズで min-max。
  - delta＝前日比の再生増（`prev_view_counter` 1 スロット）
  - rise＝delta ÷ 累計（相対成長率）
  - base＝1 話あたり累計 ÷ 初話からの日数
- **日ごとの入れ替わりが激しい**: 日次 `ranking.json` 13 日分で、Hot TOP10 が前日と重なる数は 4, 6, 4, 1, **0**, 5, 2, 5, 5, 5, 2, 3（**平均 3.5/10**）。TOP20 でも平均 11.2/20。人気 TOP（累計順）は毎日 10/10。
- **小さな新作が上位に並ぶ**: TOP20 のうち累計 1 万再生未満が 11・13・7 件（10-15〜17）。10-17 の 10 位「マゼンチュ」は**累計 148 再生**で、「薬屋のひとりごと」（累計 224 万）より上。原因は rise。前日に初めて上がった作品は delta ≒ 累計なので、rise がほぼ最大値になる。
- **前日比が取れないと黙って中身が変わる**: main にコミットされたシード（prev 無しで reproject したもの）では、全作品で `hotScore == 0.2 × baseN` が**完全に**成り立っていた（誤差 0）。前日比が欠けると Hot は「1 話あたり再生 ÷ 経過日数」に変わるが、画面には何も出ない。
- **説明と中身がずれている**: UI の ⓘ は「再生数と公開からの日数からの目安」、AGENTS.md・L1 REQ-0002 は「delta＋velocity＋recency」と書いているが、どちらも現行式と違う。カードには炎のティア（上位 10/5/1%）しか出ないので、なぜその順位なのかを確かめる手段が無い。

**試算**（日次 `works.json` の累計の差を前日比の再生増とみなして並べ直した。この方法で現行式を再現すると重なり 3.1、実際の hotScore では 2.7 で、ほぼ一致する）

| 並べ方                                    | TOP10 の前日との重なり（平均／最小） | TOP20 の前日との重なり | TOP20 のうち累計 1 万未満 |
| ----------------------------------------- | ------------------------------------ | ---------------------- | ------------------------- |
| 現行式（0.5·delta + 0.3·rise + 0.2·base） | 3.1 / 0                              | 10.4                   | 9.2                       |
| **前日比だけ**（log 正規化）              | **5.4 / 4**                          | 11.4                   | **3.3**                   |
| **前日比の指数平滑（α=0.3）**             | **7.0** / 2                          | **14.9**               | 3.8                       |
| 0.7·平滑化した前日比 + 0.3·base           | 6.6 / 1                              | 14.7                   | 6.0                       |

**提案**

1. **第 1 段（state 追加なし）**: `hotScore` を前日比の再生増 `max(delta, 0)` だけにする（log 正規化は残し、炎のティアの percentile もそのまま使える）。rise と base は外す。
   - works.json に `deltaViews`（整数 1 つ）を載せ、Hot 並びのカードに **「昨日 +1.2万」** を炎と並べて出す。
   - ⓘ 文言を「Hot＝前日からの再生数の増え方（1 日ごと・目安）」に直す。
2. **第 2 段（state を 1 つ増やすだけ）**: `state/hot-ema.json`（シリーズごとに float 1 つ・上限あり）に前日比の指数平滑を持ち、表示を「直近の 1 日あたり +N（数日の平均）」にする。無制限の履歴は持たないので、「1 スロット bounded」の方針から外れない。
3. **前日比が取れない日**（全体の delta 合計が 0、または prev が無い）は ranking.json に `hotStale: true` を立て、一覧の Hot 並びに「勢いデータ更新待ち（累計順で表示中）」と明示する。黙って別の指標に切り替えない。
4. 同じ PR で L1 REQ-0002・L2 の式・AGENTS.md の Hot の説明を新しい式に揃える。

**L0 整合**: 「隠れた重み付けをしない」。1 つの指標を数値で見せれば、ユーザーが自分で順位を確かめられる。日ごとの入れ替わりが半分以下になり、「同じ操作で同じ結果」にも近づく。

**価値 / コスト / リスク**: 価値＝高（ランキングは中核の REQ-0002）／コスト＝中（ETL・型・カード・文言。第 2 段は state ファイルの追加と deploy の確認）／リスク＝中。順位の見え方が変わる。前日比は大作が強くなる方向（例: 薬屋）に寄り、「小さいが伸びている新作」は上位から減る。新作を見たい用途は「新規シリーズ」並びとトップの新規列でまかなえる。

**優先度**: 最高（第 1 段）・中（第 2 段）。

**受け入れ条件・検証**

- 付録の試算スクリプトで、変更後の式の TOP10 の前日との重なりが平均 5 以上。
- Hot 並びのカードに前日比の数値が出る。前日比が欠けたフィクスチャでは `hotStale` の明示が出る。
- `tests/` の metrics 系テストを新しい式に更新し、現行の決定性（同点の決着）を保つ。

## A2. 検索: 表記ゆれ対策と「タグで探す」の提案 ★推奨 4

**対象ファイル**: `web/src/features/list/filter.ts`（q の照合）、`web/src/main.ts`（ロード時に正規化した題名を一度だけ作る）、`web/src/features/list/list.ts`（提案チップ）、`web/src/shared/tag-filter.ts`（正規化関数をまとめる）。

**現状（根拠）**

- 照合は `w.title.toLowerCase().includes(q.toLowerCase())` だけ。**NFKC も、ひらがな/カタカナの同一視もしていない**。
- 題名 6,946 件のうち **2,301 件（33%）が NFKC で変わる**（全角英数記号を含むもの 1,741・全角スペースを含むもの 671）。
  - `Re：ゼロ`（全角コロン）→ 0 件。NFKC で揃えれば 6 件
  - `はいきゅー` → 0 件。カナに揃えれば `ハイキュー` の 20 件に当たる
  - 題名に全角スペースが入った作品（例 `Re:ゼロから始める異世界生活　4th…`）を半角スペースで打つと当たらない
- 略称（`ガルパン`・`このすば`・`リゼロ`）は題名検索では 0 件。ただし**同じ名前のタグがある**（10・3・1 作品）。現状は `#` を付けて打たないとタグ検索にならない。
- 英題・ローマ字はデータ源に無い（対象外）。

**提案**

1. 題名も q も同じ規則で揃えてから部分一致させる: NFKC → 小文字化 → 空白を除く → ひらがなをカタカナに寄せる。正規化した題名は works の読み込み時に 1 回だけ作る（6.9k 件なので索引は要らない）。
2. q を同じ規則で揃えた結果が**タグ名と完全一致**したら、結果の上に「タグ『#ガルパン』（10 作品）で探す」というリンクを出す。押すとタグ絞り込みに移る。結果を勝手に混ぜるのではなく、ユーザーが自分で選ぶ導線にとどめる。題名検索とタグ検索を分けている §87 の設計はそのまま守る。
3. 正規化関数は `normalizeTagForMatch` と同じ場所にまとめ、タグ照合と題名照合で規則がばらつかないようにする。

**L0 整合**: 「予測どおり」。見た目が同じ文字で当たったり当たらなかったりしなくなる。タグへの導線はユーザーが押したときだけ働くので、隠れた挙動にならない。

**価値 / コスト / リスク**: 価値＝中〜高（入口がヒーロー・ヘッダ・一覧の 3 か所あり、どこからでも使う機能）／コスト＝小（web だけ）／リスク＝低（当たる範囲が広がるだけで、並び順は変わらない。空白を除くことによる誤ヒットは題名の部分一致なので小さい）。

**受け入れ条件・検証**: `Re：ゼロ`・`はいきゅー`・全角スペースを含む題名を半角で打つケースをフィクスチャで単体テストする。`ガルパン` でタグ提案が出る。正規化前に当たっていたものが正規化後もすべて当たる（既存の q 件数が減らない）ことを本番の works で確認する。

## A3. 関連シリーズ: 誤結合を直し、時系列順で見やすい位置に出す ★推奨 3

**対象ファイル**: `scripts/etl/series.mjs`（`computeFranchiseKeys` のタグ側の条件）、`scripts/fetch.mjs:940-951`（`relatedSeries` の並びと件数）、`web/src/features/detail/detail.ts`（配置と表示）。

**現状（根拠）**

- 本番: 束 351 個・所属 1,072 シリーズ。最大の束（60 作品）は**ゆるキャン△・咲-Saki-・遊☆戯☆王GX・KING OF PRISM・テニスの王子様・プリパラ…の無関係な寄せ集め**。
- 原因は、ニコニコのネタタグで語尾がたまたま「シリーズ」のものが union-find で推移的につながること。例: `公式が病気シリーズ`(16)・`お茶の間の良い子号泣シリーズ`(12)・`人間やめましたシリーズ`(7)・`テニスしろシリーズ`(5)・`はす向かいシリーズ`(5)。Fate の束（27）にも `やりたい放題シリーズ` 経由で「機動警察パトレイバー」が混ざっている。
- `relatedSeries` は束の**全員を、件数の上限なし・並びは Store の登録順**で入れている（`fetch.mjs:946-951`）。寄せ集めの束に属する作品の詳細ページには、関連リンクが 59 個、意味の無い順で並ぶ。
- 詳細ページでは関連は**各話一覧のさらに下**（`detail.ts` の末尾）。話数の多い作品では見つけにくい。

**試算**（本番 works に `computeFranchiseKeys` をそのままかけた）: 「`Xシリーズ` タグは、X を NFKC・小文字・空白除去で揃えたものが題名に含まれる作品にだけエッジを張る」と条件を付けると、

| 指標                  | 現行             | 条件付き                        |
| --------------------- | ---------------- | ------------------------------- |
| 束の数 / 所属シリーズ | 351 / 1,072      | 344 / 974                       |
| 最大の束              | 60（寄せ集め）   | 23（Fate のみ）                 |
| 上位の束              | 60, 27, 15, 14 … | 23, 14（進撃）, 13（ボトムズ）… |

所属が 98 シリーズ減る。正しい結合も一部失う（例: 「機甲猟兵メロウリンク」がボトムズの束から外れる）が、関連シリーズは「ベストエフォート・取れない作品は出さない」なので、**偽陽性を減らす方向**は L1 REQ-0014 に沿う。

**提案**

1. 上の題名を含むかどうかの条件を `〜シリーズ` のエッジに入れる（`improvement/phase3.md` §4 ① の具体案）。変更前後の束の diff を PR に添付する。
2. `relatedSeries` を**初話の投稿日（firstSeen＝支店に追加された日）の古い順**に並べ、表示上は 8 件＋「もっと見る」にする（`progressiveReveal` を使い回す）。多くは前作→続編の順になるが、まとめて再投稿された作品（例: ヒロアカは 2024 年に一括再投稿され、第7期が第2期より先に並ぶ）では放送順と食い違う。放送順の公式データは無い。
3. 詳細ページの関連を**あらすじの直後・各話一覧の前**に移す（各話より先に「シリーズの他の作品」を見せる）。

**L0 整合**: 「見やすさを説明できる」。無関係な作品を出さない。時系列順なら並びの理由をユーザーが推測できる。

**価値 / コスト / リスク**: 価値＝中〜高（詳細から次の作品へ回遊する唯一の導線）／コスト＝中（ETL と詳細 UI）／リスク＝中（束が変わる。次の日次で `series/*.json` が大量に書き換わる＝deploy の差分が大きい）。

**判断**: 試算では条件を付ければ誤結合は解消できるので、**畳まずに直す**。

**受け入れ条件・検証**: 寄せ集めの束（`公式が病気シリーズ` 経由など）が消える。Fate の束にパトレイバーが含まれない。進撃・ヒロアカ・忍たま・ヤマトの束が維持される。詳細ページで関連が各話の前に、支店に追加された日の古い順で出る。

**実装後の検証（2026-10-17）**: 本番 `state` を読み込み、日次処理と同じ `applyFranchises` をかけて `series/*.json` を書き直し、ビルドしたサイトをブラウザ（Playwright）で開いて確認した。ゆるキャン△の関連は 61 件の寄せ集め → 3 件（SEASON２・映画・SEASON３）、プリパラは 61 → 2 件、パトレイバー アーリーデイズは Fate 26 件 → 関連なし（非表示）、Fate/Zero は 26 → 22 件（8 件＋もっと見る）。進撃・ヒロアカは件数そのまま。関連の件数が変わるシリーズは 257、関連が空になるシリーズは 154。

## A4. タグ: 隠しルールを 1 か所にまとめ、curated を活かす

**対象ファイル**: `scripts/etl/tags.mjs`・`scripts/store/project.mjs`（`exportTags`）、`web/src/shared/tag-filter.ts`、`web/src/main.ts:148-154`、`web/src/features/top/top.ts`（`discoveryTags`）、`web/src/features/shared/tag-autocomplete.ts`、`web/src/features/list/list.ts`（サイドバー）。

**現状（根拠）**

- tags.json は 43,359 タグ。**34,244 個（79%）は 1 シリーズにしか付いていない**。dアニメのキュレーションタグ（`isCurated`）は 376 個あるが、**UI では一切使っていない**。L1 REQ-0003 では「候補の優先表示はしてよい」とされている。
- 「出さないタグ」のルールが 4 か所に分かれている:
  1. ETL の `EXCLUDED_TAGS`（アニメ・第1話…）
  2. ETL の候補の絞り込み（`seriesCount ≥ 2 || hasNonTitleUse`）
  3. クライアントの `isHiddenTag`（クール由来・最終回・各話番号）
  4. `top.ts` の `discoveryTags`（アニメ・第1話。1 で既に除かれているので二重）
- **トップの「Hot/人気タグ」は、隠すタグを除く前に 10 件に切っている**。本番の人気タグ 10 件には `最終回`・`2022年秋アニメ`・`2021年冬アニメ` が入っていて、クライアントで除いた分だけ少なくなる。残りにも `探してたあのセリフ・シーン@Dアニメ`・`サムネホイホイ`・`Cパートあり` といった、作品を探すのには向かないメタタグが混ざる。
- ランダムタグの母集団はほぼ全タグなので、**チップの約 8 割が 1 作品しか出ない一覧**につながる。

**提案**

1. 隠すルールを ETL に一本化する。tags.json の候補辞書とトップのタグ一覧は**隠したあとの結果で作る**。works.tags は照合用に今の値のまま残す。詳細の各話チップ用にクライアントの `isHiddenTag` を残す場合は、ETL 側と同じ規則であることを一致テストで固定する。
2. curated を先頭に出す: サイドバーのタグ欄とオートコンプリートで `isCurated` を優先して並べる（同じ平面のまま並び順だけ変える＝別の facet は作らない）。L0 の「ジャンルで気分から探せる」にあたる層になる。
3. ランダムタグの母集団を `seriesCount ≥ 5`（本番で 1,908 タグ）または curated に限る。

**L0 整合**: 「選択肢を絞って迷わせない」「ジャンルで気分から探せる」。どこに出るタグも同じ規則で選ばれる＝予測どおり。

**価値 / コスト / リスク**: 価値＝中／コスト＝中（ETL・web・テスト）／リスク＝低〜中（候補の並びが変わる。照合用のデータは変えない）。

**優先度**: 中（B3 と同じ PR にまとめると効果が見えやすい）。

## A5. 「投稿年」スライダーを「放送年」に置き換える（見送り）

> **オーナー判断（2026-10-17）: 見送り。** 放送年は全作品の約 6 割にしか無く、公式データではなくタグ由来のため。投稿年スライダーはいまのまま残す。以下は検討の記録として残す。

**対象ファイル**: `web/src/main.ts`（`workYear`・`YEAR_STOPS`・年のフィルタ）、`web/src/features/router.ts`（URL パラメータ）。

**現状（根拠）**

- `workYear` は firstAt＝**支店に投稿された年**。ⓘ にも「元の放送年とは異なる場合があります」と書いてある。
- 本番の投稿年は **2012〜2026 の範囲にしか無い**。放送季（cours）が分かる 4,127 作品のうち、投稿年と放送年が一致するのは 1,897 件（**46%**）だけ。
- 一方、放送季から見た年代は 1960 年代〜2020 年代（80 年代 142・90 年代 181・00 年代 712 作品）。「90 年代のアニメ」は**投稿年では探せないが、放送年なら探せる**。L0 の「クールごとに遡れる」とも一致する。
- クールのボタンは 202 季あり、年代の幅で遡るにはボタンが細かすぎる。

**提案**: 年のスライダーを `cours` の年の部分（放送年）にする。放送季が分からない作品（約 4 割）は、今の投稿年の扱いと同じく、範囲を指定したときは対象外にする。ⓘ には「放送季が分かる作品（約 6 割）が対象です」と書く。URL は新しいパラメータ（例 `air=`）にし、旧 `year=` は無視する（意味が変わったものを黙って読み替えない）。

**L0 整合**: ユーザーが思っている「何年の作品」と一致する＝予測どおり。

**価値 / コスト / リスク**: 価値＝中／コスト＝小（web だけ・データは works.cours に既にある）／リスク＝低（旧 `year=` のブックマークは絞り込み無しに戻る）。

**代わりの案**: 削除（クールのボタンがあるので）。ただし年代で遡る手段が無くなるので、置き換えを推奨する。

## A6. 並び替えの向きの表示を、キーごとの言葉にする（小）

**対象ファイル**: `web/src/features/list/list.ts`（`dirToggle`・適用中チップ）。

**現状**: 向きは共通トグルの「降順 ▼／昇順 ▲」。既定の降順は「良い方から」なので、**五十音順の「降順」は あ→わ**、新着系の「降順」は新しい順になる。言葉と実際の並びが逆に見える組み合わせがある。

**提案**: キーごとの言葉で出す。数値系＝「多い順／少ない順」、時刻系＝「新しい順／古い順」、五十音＝「あ→わ／わ→あ」。URL の `dir` はそのまま。

**L0 整合**: ラベルどおりに並ぶ＝予測どおり。**価値** 小〜中／**コスト** 小／**リスク** 低。**優先度**: 高（準備運動の PR）。

## A7. 詳細ページにクールを表示し、そこから辿れるようにする（小・保留）

> **保留（2026-10-17）**: A5 と同じタグ由来のデータを使うため、A5 の見送りに合わせて保留する。

**対象ファイル**: `web/src/features/detail/detail.ts`。
